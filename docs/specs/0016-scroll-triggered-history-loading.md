# 0016：向上滚动渐进加载会话历史

- 状态：Draft（2026-10-05，待用户确认；不得开始实现）。
- 来源：用户进一步明确 [0013](0013-paged-history-and-large-owner.md) 的目标体验：首次最多展示最新 10 个 turn，继续向上滑动时渐进式加载更早历史，而不是反复点击按钮。
- 关系：获批后取代 0013 第 7 条中由按钮作为主要加载入口的交互；0013 的原 owner 权威、64 MiB 本机单会话读取／IPC 上限、Relay→Web 8 MiB 单帧上限、默认最新 10 个 native turn、cursor／容量／只读降级语义均不改变。64 MiB 指 67,108,864 字节，不是把完整会话一次传给手机。

## 输入、输出与行为

1. 打开会话时仅自动展示最新至多 10 个 native turn；若最近窗口因传输预算分段，仍按 0013 自动补齐到 10 个，无需用户操作。未滚动历史前，不因为顶部加载标记进入视口就自动拉取第 11 个及更早 turn。
2. 用户在会话内容区主动向上滚动，并接近当前已加载历史顶部时，Web 自动请求一页更早历史：单次 `thread.history` 请求的 `limit` 至多 10，沿原生 opaque cursor 前进。滚动容器是会话正文，不是整个页面或输入框。到顶后继续向上滚动可逐页加载，无需反复点击“加载更早消息”。
3. 先前已取得的 turn／item 保持原时间顺序，并按原生 ID 去重。若顶部 turn 标记为 `itemsComplete: false`，优先用 `thread.history.items` 补齐该 turn 的更早 item，再继续加载更早 turn；不得让巨型 turn 的内容缺口在自动翻页时被跳过。单次 item 页仍不超过 100 item 和 0013 的传输预算。
4. 前插历史页时保持用户当前阅读锚点和相对屏幕位置，不跳到更旧页的顶部，也不被新消息拉回底部。仅当用户原本停留在最新消息附近时，实时回复才跟随滚动到底；用户阅读旧历史期间出现新内容，应保留当前位置，并提供明显但紧凑的“回到最新”入口。
5. 同一会话同时至多一个历史页请求；接近顶部不会因多次 scroll／observer 事件重复请求同一 cursor。加载完成但仍处于顶部时，只有用户再次主动向上滚动才继续下一页，避免一次手势无限预取。切换会话、stream／epoch 改变或重连时清除旧 cursor 与旧请求结果，重新从当前原 owner 构建。
6. 现有 50 个旧 turn／32 MiB Web 内存窗口继续生效；超出时按 0013 释放已越过的页，显式提示历史间隙并提供回到最新入口。本文不把 Web 缓存上限提高到 64 MiB，也不新增 Relay／Agent 的正文持久化。

## 边界与错误

- 历史已经读完时停止请求。网络断开、`HISTORY_TOO_LARGE`、`PROTOCOL_UNSUPPORTED`、无前进 cursor 或页格式错误时保留当前可见消息，停止自动重试，显示明确错误和可点击的重试入口；不得持续旋转或将 Agent 误标为离线。
- 内容不足一屏而无法产生向上滚动、键盘／辅助技术不易执行手势时，保留可访问的“加载更早消息”手动入口作为补救；它不是正常长历史浏览的必需步骤。
- 0013 现有“大 follower 同时仅一个”的进程级内存保护保持不变：第二个超过普通帧预算的实时会话可能退化为历史只读。这不改变每个会话的 64 MiB **容量门槛**，但不承诺多个大会话同时实时订阅；若用户要求并发实时能力，需另立容量预算规格。
