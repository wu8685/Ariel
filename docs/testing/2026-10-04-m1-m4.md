## 环境与范围

- macOS 本机；Codex Desktop `26.930.31730`、内置 CLI `0.160.0`。私有 IPC 只对这一配对放行。
- 所有会产生 turn 或文件变更的测试均使用 `cmd/probe fixture create` 新建的隔离临时 workspace；不对业务会话做写测试。fixture manifest 留在 `.local/`，不纳入版本控制。

## 本轮容量与重订阅回归

- Web 快速重新订阅同一 thread 时只接受当前 subscriptionId 的事件；旧快照和旧 update 不能覆盖新视图或造成重订阅风暴。先写失败测试，再修复。设备切换也会退订旧 subscription；迟到的成功回执会主动退订。
- Agent 最多缓存 64 个 thread controller、每 thread 最多 16 个订阅。无订阅的 follower 会关闭，controller 满额时只淘汰最久未用的空闲项；最近 4096 个已受理或结果未知的 message ID 在 controller 淘汰后仍去重。容量测试先红后绿。
- Relay 每 Web 最多 32 个活跃或待建立订阅，超额请求不转发。Web 断开、订阅超时或断开后迟到 accepted 时，Relay 发起幂等退订；Relay→真实 Agent 的集成测试证实 follower 被关闭。对应失败测试先于实现。
- 同机浏览器以 390×844 视口复验隔离 fixture：切换及重复选中原 thread 后历史与输入框仍可见；长标题省略显示，列表可直接关闭。真实 App Server 历史页从 50 条加载到 100 条，未出现页面错误。这仍不是物理手机验收。
- 本轮修改后重新运行 `go test -race ./...`、`go vet ./...`、`web/npm test` 和 `web/npm run build`，均通过。

## 双客户端并发启动与原生异常

- 在两个新建的无工具隔离 fixture 上，Agent Service 与独立 IPC follower 使用不同 `clientMessageId` 同时向同一 Desktop owner 尝试发送。两轮中两侧均只能判为 `unknown`，原 owner 快照均出现 canonical history 中 `status=inProgress`、`turnId` 为空、`items` 为空的条目；原生快照不能归一化。第二轮结束后独立 App Server 历史只报告 seed completed 和一个 interrupted turn，live runtime 却仍报告 active，pending request 为 0。无法从这些证据确定两次请求谁真正受理，也不能宣称完成了“外部 Desktop UI 与 Ariel 并发”的验收。
- 未对业务会话做写实验。清理器只针对确有 turn ID 的隔离 turn 尝试 exact interrupt；第二轮原生状态异常时刷新被 fail-closed 拒绝，不能安全地从 live 层确认清理回执，且不得对无 ID 条目发送停止。独立持久化历史确认已记录的实际 turn 终态为 interrupted。隔离 fixture 留在本机 `.local/`，未纳入版本控制。
- 针对异常先写失败测试，再实现 `NATIVE_STATE_UNCERTAIN`：首次订阅返回明确错误；已订阅 stream 终止、清空旧视图、禁用远程操作；Web 不对确定性的结构异常自动重订阅，用户可稍后手动重选。直接请求变更也受相同 fail-closed 检查，follower 在真正发出 start 前再次检查原生 canonical turn 是否可寻址。普通连接断开仍沿用 `RESYNC_REQUIRED` 自动恢复。清理器还限制每个 exact turn 的重复停止尝试。
- 本轮修改后 `go test ./...`、`go test -race ./...`、`go vet ./...`、`web/npm test`（13/13）及 `web/npm run build` 均通过；并发真实实验本身失败，不能算通过项。
- 同版本本地 Relay、Agent 和新构建的 Web 页面联机后，点选上述异常隔离会话，页面实际显示“会话状态无法确认”和 `NATIVE_STATE_UNCERTAIN` 提示；发送输入及按钮禁用。等候后未出现自动重订阅循环。随后切换到既有正常隔离会话，历史、`待命` 状态和可输入的消息框正常显示，说明异常仅隔离该 thread。升级过程中仍打开的旧 Web bundle 不识别新错误码，须重新载入页面取得新协议定义；这一点不同于同版本 Relay／Agent 的普通断线恢复。

## 当前 Desktop 权限与短暂原生占位

- 新建隔离 fixture 时 `thread/start` 使用 `read-only/on-request`。但 Web 自动加载后，独立 owner 观测到 `danger-full-access/on-request`；对应 rollout 的首个 turn context 是 read-only，后续 context 已变为 danger-full-access。公共 App Server `thread/read` 的 thread 和 turn 字段均无可用于恢复原权限的设置。因而不能断言自动加载保留原 sandbox；这次 `/usr/bin/true` 没有弹出命令审批，不能算作“待审批恢复”验证。没有把此现象推广到所有 Desktop 加载路径。
- [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)说明独立客户端的 `thread/resume` 可传配置覆盖，`turn/start` 的显式 sandbox 设置可成为后续 turn 默认值；但这不是 Desktop deep link 或原 owner 自动加载保留旧权限的保证。本机观测与官方文档合起来仍不足以让 Ariel 从公共历史安全还原先前权限，因此没有用独立 App Server 另起 executor，也没有猜测原权限并覆写当前 Desktop 设置。
- 规格 0004 增加当前权限可见性。归一化、协议及 Web 显示测试先红后绿；同版本本地页面实际点开该 fixture 后，头部显示“当前 Desktop：Full Access · 审批策略 on-request”及 sandbox 警示，历史和输入仍正常。只展示当前 owner 状态，不假装历史权限保持不变。用户于 2026-10-04 确认“显示警示并允许发送”，不因 Full Access 单独阻断，也不擅自修改 Desktop 权限。
- 另一隔离 fixture 的普通发送在原生启动期间短暂返回 `NATIVE_STATE_UNCERTAIN/unknown`，后续独立持久化历史显示 turn 已完成；不能据此断定与上述并发 ghost 完全同因，但立即终止订阅会造成误锁。规格 0004 现在仅对严格的 active、无请求、空 ID/空 items 的 canonical 占位允许最长 8 秒等待，期间不发布不可寻址快照，也不再次发送；恢复地址后继续原订阅，持续异常照旧 fail closed。分类、恢复和超时测试先红后绿。
- 随后补充边界 red/green：占位判定现在要求与当前 follower 的 cwd 一致，且其他历史 turn/item 至少具有可寻址身份；错误 workspace、混入 malformed item 不得借“过渡态”延迟失败。发送前的 canonical/history 与 fallback turns 也必须有完整容器和非空 turn ID；缺字段或空 ID 在调用原 owner 前即返回 `NATIVE_STATE_UNCERTAIN`。这些是原规格“结构漂移 fail closed”的细化，仍需真实 Desktop 兼容性回归。
- 用户决策后的独立 fixture `m5-full-access-send-01`：Web 点选未加载历史，自动取得同一 owner；当前显示 `Full Access / never`。先写失败测试确认 Full Access 警示不禁用 idle 发送、pending/断线仍禁用；实际页面发现旧警示文案错误地提及 on-request，再以 red/green 改为不依赖审批模式的准确警示。重新加载后发送一次明确禁止工具的独特 marker，Web 显示 inProgress→completed、精确回复且草稿清空。独立 `probe history` 返回同一 thread 2 个 completed turns、4 items；新增 opt-in 只读测试进一步在原持久化 thread 的同一 completed turn 核对独特 user marker、精确 agent 答案，且无 command/fileChange item。该成功路径不证明并发原生异常或真实权限申请已解决。
- 专用 `user-input` fixture `m5-pending-recovery-01`：Web 自动加载原 owner 后，由已验证 fixture 探针生成一个真实双问题 `request_user_input`。Web 实时出现卡片；先仅重启 Ariel Agent，再仅重启 Ariel Relay（均不退出 Codex Desktop），同一页面两次重新订阅后仍显示同一待回答问题。通过 Web 提交选项 `Blue` 与自由文本，卡片消失、turn 完成并返回预设 marker；独立 App Server 读取原 thread 为 2 个 completed turns、5 items。测试过程中未自动重发待处理请求。注意这只覆盖 Agent／Relay 重启，不代表 Desktop 退出后原生 pending request 可恢复。
- 上述真实卡片在 pending 期间暴露了历史摘要误报：“已回答补充问题”先于用户提交出现。补充规格后先写 `completed=false`／缺失／`true` 的失败测试，再把三态分别呈现为“等待补充回答”／“补充回答状态未知”／“已回答补充问题”；卡片本身仍以原 owner 当前 pending request 为准。

## Web 乱序恢复回归（2026-10-04）

- 复查 M4 的事件顺序恢复时发现：`thread.update` 序号断裂后，Web 会清空旧视图，但重订阅回调从首次渲染闭包取得空设备 ID，因此没有向 Relay 发出新的 `thread.subscribe`，页面停在“正在同步会话”。
- 先加入浏览器组件测试，模拟选中 `mac` 设备、收到首个 snapshot、随后收到跳号 update；测试实际以“只发出一次订阅”失败。修复后测试确认针对原设备重订阅、退订旧 subscription、新 snapshot 接管，旧 stream 迟到 update 不会覆盖新视图或触发重复订阅。
- `web/npm test`：9 个测试文件、34 项通过；`web/npm run build`：通过。该回归使用协议模拟事件，不冒充真实网络断帧或物理手机验收。

## Web 列表响应竞态回归（2026-10-04）

- 切换设备时，旧设备尚未完成的 `thread.list` 响应可能晚于新设备响应到达，把侧栏重新换成旧设备会话。先用双设备组件测试复现失败，再让 Web 仅接受当前设备、最新请求代次的列表结果；旧响应与旧错误不再覆盖新视图。
- `device.status` 触发的新 `device.list` 也可能先于旧列表请求返回：旧响应会把离线设备重新标为在线。先用乱序响应测试复现失败，再按最新请求代次接受设备状态；断线时使未完成的设备／会话列表请求失效。
- `web/npm test`：9 个测试文件、36 项通过；`web/npm run build`：通过。测试覆盖客户端响应乱序，不代替物理手机或 Relay／Agent 真实进程竞态验收。

## 无缓存 Go race 回归（2026-10-04）

- `go test -race -count=1 ./...` 首次发现 `TestServiceSerializesConcurrentStartsAndRejectsDuplicateID` 偶发 `accepted=2 busy=0`。调查确认测试的 attach factory 每次生成独立 `fakeLive`；无订阅时首个 Start 结束后 follower 会按设计释放，第二个 goroutine 可能才开始并取得忘记 busy 状态的新 fake owner。该观察不证明真实 Desktop owner 接受了两个 turn。
- 测试改为先保留一条订阅，使两次 Start 面向同一个 fake owner，再验证串行与 busy 结果。目标用例在 `-race -count=20` 下通过；整仓 `go test -race -count=1 ./...`、`go vet ./...` 通过。生产路径未为测试改变。

## Web 真实操作入口的组件回归（2026-10-04）

- 用通过共享协议 Schema 校验的模拟 Relay 帧，驱动完整页面而非单独卡片：选设备和原历史 → 接受 snapshot → 输入并发送，核对 `clientMessageId`、原 threadId、接受前保留草稿；后续 active turn 的停止请求携带精确 `expectedTurnId`。
- 双问题补充回答核对选项与自由文本各自映射到正确问题 ID；命令审批只出现原 owner 提供的决定，并把 `deny_and_stop` 发给原 interactionId。成功回执不抢先删除卡片，等 owner 更新；发送结果为 unknown 时保留草稿，不自动重发。
- `web/npm test`：9 个测试文件、40 项通过；`web/npm run build`：通过。这些测试覆盖浏览器状态与协议请求，但模拟 Relay 不能取代真实 Desktop 和物理手机验收。

## 尚未完成的真实验收

1. 权限请求：`item/permissions/requestApproval` 的原生 schema、Desktop follower IPC、当前请求指纹、最小单轮 grant、拒绝及 Web 卡片有单测；但本机 `codex features list` 显示 `request_permissions_tool` 为 `under development / false`，隔离 Desktop turn 直接回复工具不可用，因而没有原生待审批样例。不可把协议单测称为真实通过。未擅自修改 Desktop 全局 feature 或启动参数。
2. 物理手机：没有操作用户手机的连接或设备；同机浏览器测试不冒称手机验收。README 给出了可信局域网启动命令和安全边界。
3. Desktop 进程退出／重启：Agent 的 IPC preflight 与连续两次健康失败状态机有测试，真实 Agent 在当前 Desktop 下成功接入；未为了测试而退出承载业务会话的 Desktop。
4. 外部 Desktop UI 与 Ariel 在同一瞬间发起 turn：已有双 IPC 客户端同 owner 并发实验，但原生状态出现上述不一致，且没有进行人工 Desktop UI 点击竞赛。原 owner 无法给出可核对的消息归属时返回 unknown，不会报告已发送。该风险的成功路径尚未完成验收。
5. Desktop UI 直接发送后 Web 同步：自动化接口不允许本任务操作 Codex Desktop 自身界面，未绕过此限制。独立 IPC 客户端和原 owner 同步链路已有隔离测试，但不能冒称实际 UI 点击已验证；需用户在隔离会话中手动发一条无工具测试消息后观察 Web。

以上限制不扩大产品范围，也不隐含自动批准、离线排队或公网安全保证。
