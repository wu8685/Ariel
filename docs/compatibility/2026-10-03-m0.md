## 暴露并修正的问题

### 事件突发填满缓冲

首轮在已有消息被 owner 受理后，8 帧事件缓冲溢出，探针 fail closed。独立历史读取确认该回复已经 completed，没有按“发送失败”补发。

增加回归测试后，改为先过滤其他 thread 的状态广播，并同时限制帧数（64）和总字节数（16 MiB）；消费事件归还额度，超限仍使连接失效。随后用新的唯一测试标记再次验证。

### interrupt 的结果包装不同于 start

当前版本 `Reply.Result` 中，start 的结果为 `{"result":{"turn":...}}`，interrupt 则直接为 `{"ok":true,"interruptedTurnId":...}`。最初使用相同包装层级使回执校验失败，独立历史已确认实际中断成功。先修订 contract test 得到 red，再修订解码，最后整条写测试通过。

### 交互的 ok 不等于处理成功

只读检查发现：`getConversationRequest` 找不到请求时返回空值，`replyWithUserInputResponse` 直接返回，外层 follower handler 仍返回 ok。

随后在经 manifest 与 cwd 校验的空闲 fixture 上，提交一个带随机标记、明确不存在的 requestId；响应内容为空答案，不匹配任何真实请求。结果：

```json
{
  "missingRequestReturnedOK": true,
  "stillIdle": true,
  "nativeReceiptProvesAcceptance": false
}
```

实现约束：提交前校验 live request；不要把 ok 直接映射为 accepted。提交后请求消失只证明已不再 pending，不能单凭它判断处理者或实际答案。证据不足使用 unknown，并刷新 owner 状态。其他审批类型仍须各自实测，不能从本结果外推为已验证。

### 真实补充回答及 canonical history

专用 fixture 保持 read-only / never，沿用当前模型，仅该 fixture 的 turn 使用 Plan mode。真实 native request 包含两个问题：第一题提交实际选项 `Blue`，第二题提交选项之外的 `ariel free text`。

```json
{
  "persistedExactTurnVerified": true,
  "userInput": {
    "stage": "completed", "questionCount": 2, "receiptOK": true,
    "exactAnswerEchoVerified": true, "completed": true,
    "expiredLocallyRejected": true
  }
}
```

前序实验分别暴露出：打开 fixture 后立即连接可能超时（独立历史确认未新增 turn）；模型提问工具要求每题提供选项，不能依赖底层 Schema 的 options 可空；当前状态使用 `turnHistory.kind=canonical`，旧 `turns` 数组为空，导致初版探针在实际回答完成后仍超时。最后一项先加入 red 回归，再按 `history.islands[].entries[].value` 查 `entitiesByKey`，不接受未引用的孤立 entity，随后真机全链路通过。

成功证据为相同 request ID 类型和值、turn ID、completed userInputResponse 与全部答案精确匹配，并且 request 不再 pending；另由独立 App Server 核对该 turn 的 completed 和唯一输出标记。模型完成记录自身不能替代答案回显。`expiredLocallyRejected` 只证明完成后的本地 guard 不重发。

### 两个客户端竞争同一补充问题

另一专用 user-input fixture 中，两个独立 IPC 客户端基于同一条已核对的 pending request，同时提交不同的选项与自由文本。两个 native 回执都为 `ok`；owner 的 canonical history 仅精确回显第二客户端的整组答案，且该 request 已消失。独立 App Server 确认对应 turn completed 且回复标记唯一；探针未重试或中断。

```json
{
  "firstReceiptOK": true,
  "secondReceiptOK": true,
  "exactEchoWinner": "second",
  "completed": true,
  "cleanupStopped": false,
  "persistedExactTurnVerified": true
}
```

这只证明本次竞争的最终可见答案来自第二客户端，不证明第一个回执对应的操作被实际采纳，也不构成请求级 exactly-once 保证。产品处理必须按 live request 身份与最终 exact echo 更新状态；两个候选答案相同或回显不可得时归类 `unknown`。仅测了补充问题，不外推到审批竞争。

### 中断后的过期补充问题

在同一专用 fixture 的新 turn 中等待两个问题出现，不提交答案，而是使用 `expectedTurnId` 精确中断。刷新后的 owner 状态为 idle、无 pending，canonical history 中该 exact turn 为 interrupted。旧答案再进入提交流程时被本地 guard 拒绝，未发 IPC；独立 App Server 核对该 exact turn 已持久化为 interrupted。

```json
{
  "pendingObserved": true,
  "interrupted": true,
  "expiredLocallyRejected": true,
  "cleanupStopped": false,
  "persistedExactTurnInterrupted": true
}
```

新增 guard 还要求答题时 exact turn 必须在 live 状态中明确为 `inProgress`；未知或终态均拒绝。随后在真实 Desktop 上再次完成普通两题回答，精确回显和独立持久化核对均通过，说明该条件没有阻断当前版本的正常路径。这里验证的是 Ariel 的本地拒绝；没有向已中断的原生请求故意重发，不能声称服务端会怎样处理过期答案。

### 未加载历史的独立自动打开入口

独立 App Server 在系统临时目录创建普通无工具 fixture，完成 seed 后进程退出，未用 App 导航工具打开它。App 侧只读 `read_thread` 将该聊天标为 `notLoaded`，原 threadId 和 cwd 已知。此时 `probe owner` 两次超时，outcome 为 `unknown`；不能把超时严格写成“明确无 owner”。

随后由独立 shell 执行 macOS `open codex://threads/<fixture threadId>`，无需用户在电脑端点击。单凭 `open` 退出码不算验证；之后 `probe owner` 成功发现 Desktop owner 并获取快照，App 侧只读状态变为 idle，threadId 与 cwd 均未变化。继续对这个 fixture 运行既有的 guarded `fixture exercise`，结果如下：

```json
{
  "interruptAccepted": true,
  "liveReplyObserved": true,
  "patchBatches": 41,
  "persistedExactTurnsVerified": true,
  "snapshots": 29
}
```

这说明当前版本存在从 Desktop 之外触发原会话加载、再使用原 owner 的可行入口，且本次没有生成平行执行会话。但这仍是一次隔离实测，不是 Ariel 已实现手机端自动加载。M2 需在 Agent 中受鉴别和 threadId/cwd 校验地触发、等待 owner 出现并限时失败；还须评估 deep link 是否抢前台焦点、重复打开、Desktop 不在运行、升级和异常 URI。deep link 属于当前应用行为，不是公开稳定协议承诺。该测试聊天已归档并恢复研发界面。

## 收尾与数据

### 忙时发送的原生回执

使用无工具隔离 fixture 和两个 IPC 客户端。第一个 turn 受理后，探针确认 owner 当前状态为 `inProgress`，第二个客户端仍用开始前的 idle 快照提交。两轮实测均得到 `secondOutcome=accepted` 且 `secondSameTurnId=true`。探针对已知 turn 精确停止；独立历史只出现每轮一个被中断的 turn，未出现第二条已持久化的消息。由于立即停止，不能由此判断第二条最终会排队、steer 还是丢弃。

结论是原生 `start-turn` 回执不能替 Ariel 保证“忙时输入只留草稿”。生产 Agent 必须按 thread 串行化发送入口，在锁内刷新 owner 的最新状态，只在确认为 idle 且无 pending request 时提交；busy 时拒绝本次发送并将文字留在 Web 本地草稿。双 Web 并发和 Desktop 人工提交的窗口仍需 M2 真实联调。

### 命令审批的可选决定

read-only / on-request 专用 fixture 请求一次 `/usr/bin/true` 审批。探针识别出 `item/commandExecution/requestApproval`，原生 request ID、thread、turn、cwd 均匹配，item ID 存在。实际 `availableDecisions` 仅包含 `accept`、一个结构化决定、`cancel`，没有 decline。未打印或使用结构化决定，尚不能认定它的具体授权范围。

当前 decline-only 探针因此拒绝发送，随后精确中断该 fixture turn。独立读取确认 interrupted；这只是清理结果，不能作为命令被 decline 或 cancel 的证据。中间一次模型复用了前次中断的结果，只输出结束标记，未出现 native approval；探针没有把模型自述计作成功。

Schema 将 decline 描述为拒绝后继续，将 cancel 描述为拒绝并中断。用户确认按原生可用决定区分展示，见 [审批拒绝语义规格](../specs/0002-approval-denial-semantics.md)。

新建独立 command-cancel fixture 后，探针只对 native 提供的 cancel 作响应。回执为 ok，pending 消失，owner 的 canonical history 显示同一 turn interrupted；独立 App Server 的 thread/read 也确认 exact turn interrupted。精确停止清理没有触发。测试进程内保留真实 ID 作比较，不写报告。本地 fixture 执行记录显示嵌套 `/usr/bin/true` 请求收到 `aborted by user after 0.1s`；未观察到实际命令执行。

```json
{
  "receiptOK": true,
  "pendingCleared": true,
  "liveTurnStopped": true,
  "observedTurnStatus": "interrupted",
  "cleanupInterrupted": false,
  "persistedExactTurnInterrupted": true,
  "commandItemInPublicHistory": false
}
```

公开历史只包含用户消息与 reasoning，没有这次嵌套命令的 commandExecution item；先前要求 item 必须为 declined 的验证器因而报告失败。它已改为严格核对 exact turn 中断，并在 item 出现时额外禁止 completed 状态。不能把本结果扩展为所有审批类型或所有 Desktop 版本均支持。
